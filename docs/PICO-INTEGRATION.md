# Pico 一体化交付方案

更新：2026-09-21。本文区分当前证据与目标，不代表 UI/固件已经交付。

## 产品目标

插入硬件 → 打开 Pico 控制台 → 选择匹配板型的 Pico 固件 → 用户点击刷入 → 配网与绑定 → 在同一控制台配置模型、音色、角色 → 对话。

Pico 是产品名，不是板型。保持 `folotoy / ai-passport / esp32c3` 等兼容性标识，不改硬件引脚或假冒板型。

## 架构决定

沿用现有完整管理模块，不另建一个只能编辑 YAML 的替代控制台：

- Mac：manager-web（Pico 控制台）、manager-api、pico-server、固件构建工具链。
- MySQL / Redis：管理模块必需基础设施；具体部署位置、未占用端口须在部署时核实，不能假设已经存在。
- 95：FunASRServer、PaddleSpeech 常驻 systemd 服务。
- Mac 本地 LLM 网关：127.0.0.1:4317；服务端调用，不将凭据发给浏览器或写入固件。
- 云服务器：设备访问的反向代理入口，不运行语音模型。
- ESP-IDF 属于固件构建依赖，独立安装，供 pico-esp32 使用；日常用户只使用控制台。

## 控制台需要补齐的功能

1. **固件中心**：匹配板型、芯片、flash、版本和分区信息，分别展示 USB 全量镜像与 OTA 应用镜像，禁止混用。
2. **USB 刷写**：串口授权、识别芯片、选择已验证产物、显式确认、进度、失败恢复；默认不整片擦除。
3. **构建任务**：固定板型参数白名单，后台调用 scripts/build.py，不提供任意 shell 命令输入；产物记录 SHA-256、分区地址与构建配置。
4. **首次连接向导**：明确区分 USB 烧录、Wi-Fi 配网、OTA 地址迁移和设备绑定；现有代码没有证明可直接通过 USB 写入 Wi-Fi，所以不能承诺插线即全自动完成配网。
5. **管理配置迁移**：将当前 GatewayLLM、FunASRServer、PaddleSpeechTTS 的有效配置导入管理数据库，再切换 manager-api 模式；保留可回滚 YAML，不能只打开前端就算完成。
6. **配置生效状态**：保存成功、服务加载成功、设备在线与真实对话成功应分别显示。

## 端口与安全边界

- 已部署语音端口不变：Mac 8000 / 8003；95 18100 / 18120。
- 95 上后续 Pico 模型服务使用预留范围 18100–18199，分配前检查冲突。这是端口范围，不是 IP 网段。
- 管理入口可沿用仓库既有 8002 设计；部署前仍需确认监听、代理与认证。
- 0.0.0.0 是绑定地址，不是浏览器访问地址。公网仅代理必要设备路径；管理、数据库、构建接口不能无认证公开。
- USB 浏览器刷写方案应在目标 Chrome/Edge 与 localhost 安全上下文下验证；公网 HTTP 控制台不能直接视为可用的刷写环境。
- 当前公网 OTA/WS 为 HTTP/WS 过渡配置；正式远程使用应部署 HTTPS/WSS，避免明文传输。
- 不回写历史 Liquibase 脚本；若数据库种子数据含旧名称，通过新增迁移或管理 API 修正。
- 上游仓库、依赖命名、许可证和模型文件身份不能盲目字符串替换；对用户展示的产品名统一 Pico。

## 验收顺序

1. 管理模块部署与登录；模型配置迁移、保存、读取验证。
2. 品牌残留分类整改，部署后页面与回复不再冒出旧产品名称。
3. ESP-IDF 安装、匹配板型构建，校验产物分区及芯片。
4. 控制台 USB 刷写功能测试，真实硬件写入由用户确认触发。
5. 验证设备 NVS 中旧 OTA 地址已迁移，设备请求 Pico OTA 并获得 Pico WebSocket。
6. 设备 → Mac → 95 ASR → Mac LLM 网关 → 95 TTS → 设备真实对话测试。
7. 重启与断线恢复验证。

只有以上全部通过，才可以声称“以后只需插上设备、打开控制台配置即可”。
